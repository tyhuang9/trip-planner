# Unsigned Android App Bundle evidence

Dupert's **Android unsigned artifact** workflow builds and inspects both Android
release formats from the same synced native-production source tree:

- `app-release-unsigned.apk` remains ephemeral and is inspected as documented in
  [Web and native build profiles](build-profiles.md).
- `app-release.aab` is validated, copied to the conspicuously named
  `Dupert-UNSIGNED-NOT-INSTALLABLE.aab`, and retained for seven days with a raw
  SHA-256 file and a build-context record.

The App Bundle is cooperative continuous-integration evidence. It is unsigned,
cannot be installed directly, is not submitted to Google Play, and is not a
release artifact, attestation, or release-readiness gate. The workflow uses no
keystore, signing credential, store credential, production secret, emulator, or
physical device.

## Build and inspection contract

The hosted job uses Java 21 and the repository's pinned Gradle wrapper to run
`:app:bundleRelease` with code signing absent. The dedicated checker requires the
canonical `app-release.aab` filename and fails closed unless all of these checks
pass:

1. The AAB is a regular ZIP whose central directory is parsed directly so raw
   member names and external file types are inspected without line-oriented
   tool output. Entries must be safe and unique and contain only regular files
   and directories. Absolute, ambiguous, parent-traversal, backslash, duplicate,
   control-character, non-UTF-8, encrypted, extra-field, unsupported-creator,
   symlink, and special-file entries are rejected before extraction. Local and
   central names/flags must match, and Info-ZIP alternate Unicode-name handling
   is disabled for both integrity checking and extraction.
2. `BundleConfig.pb`, the base module manifest, and
   `base/assets/public/index.html` are present. JAR signature entries are absent.
3. Google's official bundletool 1.18.3 validates the bundle and reports the
   exact source-controlled contract: application ID
   `io.github.tyhuang9.dupert`, version code `1`, version name `1.0`, minimum SDK
   24, and target SDK 36.
4. JDK `jarsigner -verify` returns only the narrowly accepted Java 21 unsigned
   result. A signed bundle, unexpected status/signal/output, or tool failure is
   rejected.
5. Only `base/assets/public/**` is extracted into a temporary directory, then
   the existing packaged native-bundle policy rejects browser-only code,
   configured browser values, unsupported filesystem entries, and a missing
   packaged entrypoint.

The workflow downloads bundletool from
[Google's official GitHub release](https://github.com/google/bundletool/releases/tag/1.18.3)
and verifies its bytes before execution:

- Version: `1.18.3`
- Asset: `bundletool-all-1.18.3.jar`
- SHA-256: `a099cfa1543f55593bc2ed16a70a7c67fe54b1747bb7301f37fdfd6d91028e29`

That digest matches both the digest published by GitHub for Google's release
asset and an independent SHA-256 calculation over the downloaded JAR. Bundletool
is a separately pinned workflow tool; it is not supplied by the Android SDK or
the Gradle wrapper.

## Downloading and checking hosted evidence

Use the run attached to the exact reviewed commit. In its **Artifacts** section,
download the item named
`dupert-UNSIGNED-NOT-INSTALLABLE-<source-head-sha>`. It contains exactly:

- `Dupert-UNSIGNED-NOT-INSTALLABLE.aab`
- `Dupert-UNSIGNED-NOT-INSTALLABLE.aab.sha256`
- `BUILD-CONTEXT-NOT-ATTESTATION.txt`

After extraction, verify the recorded bytes from that directory:

```bash
sha256sum --check Dupert-UNSIGNED-NOT-INSTALLABLE.aab.sha256
```

The expected result names the AAB and reports `OK`. Then inspect the build-context
file and require its warning, source head SHA, checked-out SHA, workflow-run URL,
bundletool version/digest, AAB digest, and runner OS/architecture to match the
reviewed run. The workflow summary repeats the warning and AAB digest.

The checksum detects changes after the job wrote its evidence directory, but it
is generated by the same cooperative job as the AAB. It is not an independent
signature, trusted timestamp, protected-ref attestation, or reproducible-build
proof. A pull request can change code that runs before inspection. Treat the
evidence as a review aid, not as a secure software-supply-chain statement.

## Local verification

After building and syncing the public native-production CI profile, run from
`frontend/android/`:

```bash
./gradlew :app:bundleRelease --no-daemon
```

Download and checksum the exact bundletool version above, then run from
`frontend/` with an absolute JAR path:

```bash
BUNDLETOOL_JAR_PATH=/absolute/path/to/bundletool-all-1.18.3.jar \
  npm run check:android-unsigned-bundle -- \
  android/app/build/outputs/bundle/release/app-release.aab
```

Do not add signing options or credentials to reproduce this check. A signed AAB
belongs to a separate controlled release workflow with external secret storage,
approved signing identities, stronger provenance, and its own review.

## Retention, limitations, and rollback

The evidence upload uses read-only repository permissions, a full-commit action
pin, no compression of the already compressed AAB, and seven-day retention.
Uploads from pull requests are limited to branches in this repository; fork pull
requests can run validation but do not publish the AAB. Push and manual runs may
publish after every validation succeeds.

Passing this job does not establish installability, Play acceptance, signing,
artifact provenance, dependency publisher identity, runtime behavior, device
compatibility, store policy compliance, or release approval. The mobile
release-readiness ledger remains blocked until its signed-artifact and device
requirements are satisfied.

To roll back this evidence slice, revert its checker, fixtures/tests, package
scripts, workflow additions, and this document. Existing uploaded evidence
expires automatically. No database, deployment, signing, store, device, or user
data rollback is required.
